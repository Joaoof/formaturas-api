1. O que a gente queria fazer

Colocar uma API (um programa que responde a requisições pela internet) rodando 24 horas por dia, num servidor lá longe, para que qualquer pessoa pudesse acessar pelo endereço http://191.101.78.252.

E mais: a gente queria que, toda vez que alguém alterasse o código no GitHub, a versão nova subisse automaticamente — sem precisar mexer no servidor de novo.

Analogia: É como se você criasse um site num caderno, e cada vez que trocasse uma frase no caderno, todas as impressões espalhadas pelo mundo se atualizassem sozinhas. 🪄

2. Palavras que você precisa entender

Antes de mostrar o passo a passo, aqui está uma lista de termos técnicos com uma explicação bem simples de cada um. Para cada palavra, sugiro o que você deve pesquisar para se aprofundar.

VPS (Virtual Private Server)

Um computador que fica ligado 24h por dia numa empresa de hospedagem. Você aluga ele por mês (~R$25) e tem acesso remoto como se fosse a sua máquina. Diferente do "hospedagem de site tradicional", aqui você é o dono, instala o que quiser.

Pesquise: "o que é uma vps", "vps vs hospedagem compartilhada", "melhores provedores de vps para iniciantes"

SSH (Secure Shell)

É como se fosse um controle remoto criptografado que te deixa digitar comandos na VPS a partir da sua máquina. Você não fica olhando a tela dela: você digita e o que digitou é executado lá.

Pesquise: "como funciona ssh", "ssh chave publica privada", "openssh windows"

Docker

Um programa que empacota sua aplicação junto com tudo que ela precisa para rodar (o .NET, as bibliotecas, o sistema) num pacote chamado container. O container roda igual em qualquer computador — mata o famoso "na minha máquina funciona".

Pesquise: "o que é docker", "docker container vs vm", "dockerfile explicação"

Docker Compose

Um arquivo YAML (docker-compose.yml) que descreve vários containers rodando juntos. No nosso caso: um pra API, um pro banco de dados PostgreSQL, e um pro Watchtower (o "atualizador automático").

Pesquise: "docker compose para que serve", "docker-compose.yml exemplo"

Container Registry (GHCR)

Um lugar na internet que guarda as versões das suas imagens Docker, tipo um "Google Drive" mas para containers. Usamos o GHCR, que é o registry do GitHub e é grátis pra repositórios pequenos.

Pesquise: "github container registry", "docker registry o que é"

CI/CD (Integração e Entrega Contínuas)

Uma automação que, quando você faz git push, uma máquina do GitHub roda os testes, monta o container e publica em algum lugar. Você não precisa buildar nada manualmente.

Pesquise: "o que é ci cd", "github actions basico", "pipeline devops"

GitHub Actions

O robô do GitHub que roda scripts (chamados de workflows) quando algo acontece no repositório. No nosso caso, quando alguém faz push na branch main, ele builda o container e publica.

Pesquise: "github actions tutorial", "yaml workflow github actions"

Watchtower

Um programa que fica vigiando o GHCR de tempos em tempos. Quando ele vê que tem uma versão nova da API disponível, ele puxa e reinicia o container automaticamente. É o "olheiro" que a gente colocou na VPS.

Pesquise: "watchtower docker auto update", "nickfedor/watchtower github"

Firewall (UFW)

Uma "parede" que filtra quais portas do servidor podem ser acessadas de fora. Fechamos tudo, e só deixamos abertas a 22 (SSH pra gente entrar) e a 80 (HTTP pra API responder).

Pesquise: "o que é firewall", "ufw ubuntu tutorial"

Fail2ban

Um segurança que fica monitorando tentativas de invasão. Se alguém tenta chutar sua senha 5 vezes, o fail2ban bane o IP daquela pessoa por 10 minutos.

Pesquise: "fail2ban o que é", "protegendo ssh contra brute force"

3. O que a gente fez, passo a passo

1

Alugamos a VPS

Escolhemos uma VPS com Ubuntu 24.04 LTS (a versão estável do Linux). O provedor nos deu um IP público (191.101.78.252) e uma senha do usuário root (o "super-administrador" do Linux).

Pesquise: "ubuntu server iniciante", "linux vs windows server"

2

Geramos uma chave SSH

Em vez de usar senha (que é fraca), a gente gerou uma "chave" criptográfica na máquina Windows. Isso cria dois arquivos: uma chave privada (que fica em segredo no seu computador) e uma chave pública (que a gente coloca na VPS).

ssh-keygen -t ed25519 -f $env:USERPROFILE\.ssh\id_ed25519 -N '""'

Pesquise: "como gerar chave ssh ed25519", "chave publica x chave privada"

3

Conectamos na VPS pela primeira vez

Usando a senha do root, a gente entrou na VPS. Dentro dela, colamos a chave pública no arquivo authorized_keys. A partir daí, o SSH aceita a chave e não pede mais senha.

ssh root@191.101.78.252
# lá dentro:
echo "SUA_CHAVE_PUBLICA" >> ~/.ssh/authorized_keys

Pesquise: "ssh sem senha chave publica", "authorized_keys funcionamento"

4

Rodamos um script que preparou a VPS

Escrevemos um script (install.sh) que faz tudo isso de uma vez:

  • Atualiza o sistema operacional
  • Instala o Docker
  • Configura o firewall (só abre porta 22 e 80)
  • Liga o fail2ban
  • Cria um usuário deploy (o root nunca deveria rodar apps — má prática de segurança)
  • Desabilita login por senha e login como root pelo SSH

Pesquise: "hardening ubuntu server", "principio do menor privilegio", "shell script bash tutorial"

5

Configuramos o "cofre" de segredos

Na VPS, criamos um arquivo .env com as senhas e chaves secretas que a aplicação precisa: senha do banco de dados, chave para assinar tokens JWT, token do GitHub, etc. Esse arquivo nunca vai pro Git — fica só na VPS.

Pesquise: "variaveis de ambiente boas praticas", ".env arquivo o que é", "gitignore segredos"

6

Subimos os containers

Com o comando docker compose up -d, o Docker baixou as imagens da internet, criou 3 containers rodando ao mesmo tempo:

  • formaturas-api — a nossa aplicação .NET
  • formaturas-postgres — o banco de dados
  • formaturas-watchtower — o "atualizador automático"

Pesquise: "docker compose up d flag", "postgresql docker volume persistente"

7

Configuramos o CI/CD (a mágica)

No GitHub, criamos um workflow (um arquivo em .github/workflows/build-and-push.yml) que roda toda vez que alguém faz git push. Esse workflow:

  • Baixa o código
  • Builda a imagem Docker
  • Publica essa imagem no GHCR (Container Registry do GitHub)

Pesquise: "github actions build docker", "docker buildx github actions"

5. A mágica: deploy automático

Depois de tudo configurado, o fluxo do dia-a-dia ficou ridiculamente simples:

1. Você edita o código no seu computador
2. git add .
3. git commit -m "mudanca X"
4. git push origin main

--- e é isso ---

O GitHub Actions builda automaticamente (~1min)
Publica a imagem nova no GHCR
O Watchtower na VPS detecta em ≤60 segundos
Reinicia o container com a versão nova
A API atualizada está no ar em ~2 minutos

Você nunca mais precisa acessar a VPS para atualizar código. Tudo é automático.

6. Onde aprender mais

Cursos gratuitos que recomendo

  • Curso em Vídeo (Gustavo Guanabara) — Fundamentos de programação, HTML/CSS, Python. Ótimo para começar.
  • Rocketseat — Cursos gratuitos de web, mobile, Node.js. Muito visual e prático.
  • Filipe Deschamps (YouTube) — Explicações claras sobre conceitos avançados.
  • fullcycle.com.br — Docker, Kubernetes, arquitetura de sistemas.

Ordem sugerida de estudo (do zero até aqui)

  1. Lógica de programação (Python ou JavaScript)
  2. Git e GitHub (fluxo de commits, branches, pull requests)
  3. HTTP e APIs REST (verbos GET/POST/PUT/DELETE, JSON, status codes)
  4. Linux básico (comandos de terminal, permissões)
  5. SSH e servidores remotos
  6. Docker (containers, images, volumes)
  7. Docker Compose (múltiplos containers)
  8. GitHub Actions (workflows, CI/CD)
  9. Bancos de dados (PostgreSQL / SQL básico)
  10. Boas práticas de segurança (chaves SSH, firewall, gerenciamento de segredos)

Livros que vão te fazer entender tudo

  • "O Pragmático Programador" — Dave Thomas & Andy Hunt (mentalidade de programador)
  • "Docker: Do desenvolvimento à produção" — Casa do Código
  • "The Linux Command Line" — William Shotts (grátis em linuxcommand.org)
Dica de ouro: não tente aprender tudo de uma vez. Escolhe um tópico, faz um mini-projeto, vê funcionando, aí vai pro próximo. A programação é uma escada — degrau por degrau.
